# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` / line 72-74 | Returns `{"status": "ok"}` statically without testing connectivity to MongoDB. Contract requires 200 only when MongoDB answers a ping, otherwise 503. | Stopping MongoDB or setting an invalid `MONGO_URI` still causes `GET /health` to return 200 OK instead of 503 Service Unavailable. | Pinned the MongoDB connection using `client.admin.command('ping')` in a try/except block; returns 200 on success and raises HTTP 503 on failure. |
| 2 | Startup / lines 22-24 | No database indexes are created at startup. Unique constraints on `emp_code` and `(emp_code, date)` are completely absent, violating the environment and data model contracts. | Inspecting MongoDB collection metadata shows only `_id_`; concurrent inserts with identical `emp_code` succeed, corrupting uniqueness. | Implemented a FastAPI `lifespan` handler that idempotently creates unique indexes (`emp_code`, `(emp_code, date)`) and query/aggregation indexes (`(date, emp_code)`, `(department, joined_on)`, etc.) before serving requests. |
| 3 | `create_employee` / line 79-83 | Uses check-then-insert (`find_one` followed by `insert_one`), which is vulnerable to race conditions under concurrent requests. | Sending two simultaneous `POST /employees` requests with identical `emp_code` results in duplicate documents or unhandled race conditions. | Enforced database uniqueness via unique index on `emp_code`, removed check-then-insert, and caught `DuplicateKeyError` to return HTTP 409. |
| 4 | `create_employee` / line 82-85 | Stores and returns `created_at` as a naive Python `datetime.now()`, which FastAPI serializes to an ISO string instead of epoch milliseconds. | Client validation fails; `created_at` is an ISO-8601 string rather than an integer count of epoch milliseconds (`EpochMillis`). | Stored UTC BSON datetime in MongoDB and converted `created_at` to integer epoch milliseconds in the API response. |
| 5 | `EmployeeIn` / line 53-61 | Missing input validation: no regex validation on `emp_code` (`^EMP\d{4,6}$`), no validation on email format, no string length limits, and no check that `shift_start != shift_end`. | Submitting `shift_start == shift_end` (e.g., "09:30" and "09:30") or malformed email returns 201 Created instead of 422 Unprocessable Entity. | Added Pydantic field validators with patterns and length constraints matching `openapi.yaml`, and a model validator rejecting requests where `shift_start == shift_end`. |
| 6 | `list_employees` / line 93 | Incorrect pagination skip logic: `skip = page * page_size`. Since `page` starts at 1, querying page 1 sets `skip = 20`, dropping the first 20 employees. | Querying `GET /employees?page=1&page_size=20` returns employees 21 to 40 instead of employees 1 to 20. | Fixed calculation to `skip = (page - 1) * page_size`. |
| 7 | `list_employees` / line 94 | Total count ignores filters: `total = db.employees.count_documents({})` counts the entire collection rather than filtered results. | Querying `GET /employees?department=Sales` returns the total count of all employees in the company instead of Sales department headcount. | Updated count to reflect applied filters: `total = db.employees.count_documents(q)`. |
| 8 | `list_employees` / line 95 | Missing required sort order: returns documents in arbitrary MongoDB natural insertion order. Contract requires sorting by `emp_code` ascending. | Employees are returned out of order when paginating. | Added `.sort("emp_code", 1)` to the MongoDB query cursor. |
| 9 | `compute_late_minutes` / line 33-37 | 1) Modifies hours/minutes of UTC `punch_in` with IST shift times without timezone conversion. 2) Uses `minutes > 10`, which returns 0 for 10 minutes and 1 second (should be 10 min per R2). 3) Fails overnight shifts. | For a 09:30 shift, punch-in at 09:40:01 IST returned 0 instead of 10. For UTC timestamps, it mixed UTC and IST times causing incorrect calculations. | Converted `punch_in` to IST, determined the proper shift start instant on the attendance date, and checked `(punch_in - shift_start).total_seconds() > 600` before taking the integer floor of elapsed minutes. |
| 10 | `compute_work_hours` / line 40-41 | Uses Python built-in `round()`, which applies banker's rounding (round half to even) rather than round half-up required by R4. Also fails to truncate input timestamps to whole seconds (R1). | Values ending in midpoint .XX5 round down to even numbers instead of rounding up to the nearest hundredth. | Truncated inputs to whole seconds, converted difference to seconds, and rounded hours using `Decimal.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 11 | `compute_overtime` / line 44-48 | 1) Does not enforce the 30-minute minimum threshold (R3). 2) Combines naive date string with `tzinfo=IST` causing type errors when compared with naive UTC times. 3) Fails overnight shifts where `shift_end` is on the next calendar day. | An employee punching out 15 minutes after shift end received 15 minutes overtime instead of 0. Comparing datetimes threw `TypeError: can't compare offset-naive and offset-aware datetimes`. | Advanced shift end by 1 day for overnight shifts (`shift_end <= shift_start`), ensured unified UTC/IST timezone handling, and returned overtime only if elapsed minutes >= 30, else 0. |
| 12 | `punch_in` / line 100-106 | 1) Does not check if employee exists; dereferencing `emp["shift_start"]` on missing employee raises unhandled `TypeError` (500). 2) Vulnerable to check-then-insert race condition. | Punching in with an invalid `emp_code` returns 500 Internal Server Error instead of 404 Not Found. Concurrent punch-ins can cause duplicate logs. | Checked `if not emp: raise HTTPException(404, ...)`, created a unique compound index on `(emp_code, date)`, and caught `DuplicateKeyError` to return HTTP 409. |
| 13 | `punch_in` / line 102-103 | Attendance date logic ignores overnight shifts (R1). The date is derived solely from the punch calendar date. | A night-shift employee (22:00 - 06:00) punching in at 00:30 IST on July 7th had attendance attributed to July 7th instead of the shift's starting date of July 6th. | Implemented R1 attendance date logic: if `shift_end <= shift_start` and punch-in IST time is strictly earlier than `shift_end`, attendance date is set to `IST_date - 1 day`. |
| 14 | `punch_in` / line 119 | Injects an unwanted `id` field: `doc["id"] = str(res.inserted_id)`. Section 5 and `AttendanceRecord` schema state that attendance records have no ID. | Response body fails OpenAPI contract validation due to extra/unexpected `id` field. | Removed the `id` assignment; returned only the required `AttendanceRecord` fields. |
| 15 | `list_attendance` / line 144-147 | Memory and scalability defect: executes `list(db.attendance_logs.find(q))` loading all documents into application memory and sorting in Python. | High memory consumption and request timeouts on large (100k) collections; causes full collection scans (`COLLSCAN`). | Delegated filtering, sorting (`.sort([("date", -1), ("emp_code", 1)])`), and pagination (`.skip(...).limit(...)`) directly to MongoDB, backed by compound index `(date, emp_code)`. |
| 16 | `list_attendance` / line 137-141 | Fails to validate `date_from > date_to`. Contract specifies `date_from > date_to -> 422`. | Supplying `date_from=2026-07-10&date_to=2026-07-05` returned 200 OK with empty items instead of 422. | Added validation check raising HTTP 422 when `date_from` and `date_to` are provided and `date_from > date_to`. |
| 17 | `list_attendance` / line 148-150 | Documents return raw BSON datetimes or ISO strings instead of integer epoch milliseconds, and legacy records omitting `half_day` or `history` are returned without defaults. | Schema validation fails on timestamps; clients encounter missing fields on legacy documents. | Serialized all date/time fields (`punch_in`, `punch_out`, `history[].at`, `history[].changes`) as epoch milliseconds and defaulted missing `half_day` to `False` and `history` to `[]`. |

## Items examined and confirmed NOT to be defects
- **`emp_code` immutability**: There is intentionally no endpoint to update an employee's `emp_code`. OpenAPI notes that `emp_code` is a permanent customer business key that never changes.
- **Absence of endpoints for `ABSENT` / `LEAVE`**: Neither punch-in nor punch-out creates `ABSENT` or `LEAVE` records. DATA_MODEL.md clarifies that these statuses originate exclusively from seeded back-office records or manual regularization PATCH.
- **Omission of `history` and `half_day` in legacy records**: DATA_MODEL.md explicitly documents sample 9 as a legacy record omitting these fields; treating missing values as `[]` and `false` respectively is the specified design, not a database corruption.
